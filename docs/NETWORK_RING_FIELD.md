# Кольцевое поле и «свой игрок всегда в центре» — заметки для сетевой части

Документ для того, кто делает мультиплеер Atacoola (сервер, матчмейкинг, синхронизация).
Описывает, как сейчас устроено поле, что уже готово для онлайна и что осталось сделать,
чтобы каждый игрок видел себя в центре экрана.

Актуально для ветки `ring-field-streak`, версия 0.4. Все числа — из `scripts/cfg.gd`.

---

## 1. Зачем это нужно

Поле поделено на 5 вертикальных дорожек. Серфер двигается только вверх-вниз по своей дорожке.
Если поле обычное (с краями), игроки на крайних дорожках в неравных условиях: у них сосед только
с одной стороны, угрозы приходят из-за края экрана без предупреждения, целей для ракет меньше.
Для PvP это нечестно.

Решение: **поле замкнуто по горизонтали в кольцо** (как в Pac-Man или Asteroids). Что ушло за
правый край, выходит из-за левого. На кольце из 5 дорожек у каждой дорожки ровно по 2 соседа
с каждой стороны — все позиции одинаковые. Поэтому любого игрока можно **нарисовать в центре**,
сдвинув остальных по кругу, и картина останется честной и правильной.

```
Мир (сервер), дорожки:          0    1    2    3    4
Клиент игрока с дорожки 4 видит: 3    4    0    1   [2] ← он сам в центре
Клиент игрока с дорожки 0 видит: 3    4   [0]   1    2
```

Сдвиг — это **параллельный перенос по кругу**, не зеркало. Лево остаётся левом, право — правом.

## 2. Что уже сделано (в одиночной игре с ботами)

Сейчас игра одиночная: живой игрок всегда на дорожке `PLAYER_LANE = 2` (центр), боты на 0, 1, 3, 4.
Поэтому «игрок в центре» пока получается сам собой. **Сдвига вида для произвольной дорожки ещё нет** —
это часть сетевой работы (раздел 4). Но вся игровая логика уже работает на кольце, так что любая
дорожка уже честная.

### 2.1. Геометрия

| Константа | Значение | Что это |
|---|---|---|
| `W` | 1080 | Ширина поля (и окружность кольца), px |
| `LANES` | 5 | Дорожек |
| `LANE_W` | 216 | Ширина дорожки, px |
| `lane_x(lane)` | `LANE_W * (lane + 0.5)` | Центр дорожки: 108, 324, 540, 756, 972 |
| `PLAYER_LANE` | 2 | Дорожка живого игрока в одиночной игре |

Координата Y обычная (растёт вниз), кольцо только по X.

### 2.2. Функции кольца — `scripts/cfg.gd`

```gdscript
## X в пределах поля 0…W.
static func wrap_x(x: float) -> float:
	return fposmod(x, W)

## Кратчайшее смещение по X от b до a по кольцу (от −W/2 до W/2).
static func wrap_dx(a: float, b: float) -> float:
	return fposmod(a - b + W * 0.5, W) - W * 0.5

## Расстояние между точками с учётом кольца.
static func ring_dist(a: Vector2, b: Vector2) -> float:
	return Vector2(wrap_dx(a.x, b.x), a.y - b.y).length()

## Сдвиги, на которых нужно нарисовать объект полушириной r в точке x,
## чтобы у края его половинки были видны с обеих сторон (margin — запас на широкие экраны).
static func ring_copies(x: float, r: float, margin: float = 400.0) -> Array:
	...  # возвращает [0], [0, W] или [0, -W]
```

**Правило:** все горизонтальные расстояния и столкновения считаются через `wrap_dx` / `ring_dist`,
все движущиеся X после шага приводятся `wrap_x`, всё, что может стоять у края, рисуется через `ring_copies`.

### 2.3. Где это применено

| Объект | Файл | Как работает на кольце |
|---|---|---|
| Акула | `shark.gd` | Появляется тенью в случайном X, плывёт, `base_x` и `position.x` через `wrap_x`. Проплыв один круг (`travelled >= W`) и снова став тенью, уходит на глубину (fade). Рисуется через `ring_copies` |
| Большая акула | `big_shark.gd` | То же; зона укуса `in_hit_zone()` считает dx через `wrap_dx` |
| Торнадо | `main.gd` `_update_tornadoes` | Появляется в случайном X полосы, идёт один круг (`path >= W`), попадание через `wrap_dx` |
| Молния | `main.gd` `_update_lightning` | Цель в случайном X (`wrap_x`), попадание через `ring_dist`. Рисуется на сдвигах 0, ±W |
| Бомба | `main.gd` `_throw_bomb`, `_update_bombs` | Цель приводится `wrap_x`, взрыв через `ring_dist`, рисуется через `ring_copies` |
| Ракета | `main.gd` `_fire_rocket`, `_update_rockets` | Летит по X с `wrap_x`, дальность `ROCKET_RANGE = 2 * LANE_W + ROCKET_HIT` (ровно до 2-й соседней дорожки, через край тоже), попадания через `ring_dist` |
| Укусы | `main.gd` `_check_bites` | `ring_dist` |
| Боты | `main.gd`, `surfer.gd` | Все проверки опасности и прицеливание через `ring_dist` / `wrap_dx` |
| Серферы | `surfer.gd` | X всегда `lane_x(lane)`, по горизонтали не двигаются, через шов не переходят |

### 2.4. Что пока привязано к дорожкам «в лоб» (важно для сдвига вида)

Эти места рисуют по **мировой** дорожке и при сдвиге вида должны рисовать по **видимой**:

- `main.gd`, `_draw_beach()` — лежаки: `var cx := C.lane_x(s.lane)`.
- `main.gd`, `_draw()` — подсветка своей дорожки: `C.LANE_W * C.PLAYER_LANE`.
- `main.gd` — всплывающие тексты над лежаками: `C.lane_x(thrower.lane)`, `C.lane_x(player.lane)`.
- `main.gd`, салют победителю — `C.lane_x(winner_lane)`.
- `surfer.gd`, `setup()` и `_respawn()` — `position = Vector2(C.lane_x(lane), C.LOUNGER_Y)`.
- Метки гибели `death_marks` хранят мировой `x`.
- Сундуки и кубки (`chest.gd`) — `position` в мировых X, тап по ним сравнивается с позицией касания.
- Прицел бомбы `aim_pos` — координаты касания на экране.

## 3. Важные свойства для сетевого кода

1. **Сдвиг — это перенос, а не отражение.** Свайп влево на клиенте = выстрел влево в мире.
   Направление ракеты (`dir = ±1`) при переводе координат **не меняется**.
2. **Сдвиг кратен ширине дорожки:** `shift = (PLAYER_LANE - my_lane) * LANE_W`.
   Поэтому дорожки при сдвиге переходят в дорожки, а не «между ними».
3. **Порядок соседей одинаковый у всех.** Для игрока с дорожки 0 сосед слева — дорожка 4. Ракета
   влево из дорожки 0 летит в мире от x=108 к x=0, выходит у x=1080 и попадает в дорожку 4.
4. **Y не меняется вообще.** Вал, зоны, пляж — общие для всех.
5. **Расстояния не зависят от сдвига:** `ring_dist` даёт одно и то же в мировых и в видимых координатах.
   Значит, столкновения можно считать в любой из систем — результат совпадёт.

## 4. Как сделать «свой игрок в центре» в онлайне — рекомендуемый способ

### Идея: переводить координаты на границе сети

Сервер считает всё в **мировых** координатах. Клиент переводит всё, что пришло с сервера,
в **локальные** координаты, где его игрок — на дорожке `PLAYER_LANE` (2), и переводит обратно
всё, что отправляет. Тогда весь существующий клиентский код (отрисовка, камера, интерфейс)
работает без изменений, как в одиночной игре.

```gdscript
# На клиенте, после того как сервер сообщил, какая дорожка у этого игрока:
var my_lane: int                       # дорожка игрока в мире (0…4)
var lane_shift: int                    # на сколько дорожек сдвигать
var x_shift: float                     # на сколько пикселей сдвигать

func set_my_lane(lane: int) -> void:
	my_lane = lane
	lane_shift = C.PLAYER_LANE - lane
	x_shift = lane_shift * C.LANE_W

# мир → экран клиента
func to_local_lane(world_lane: int) -> int:
	return posmod(world_lane + lane_shift, C.LANES)

func to_local_x(world_x: float) -> float:
	return C.wrap_x(world_x + x_shift)

# экран клиента → мир
func to_world_lane(local_lane: int) -> int:
	return posmod(local_lane - lane_shift, C.LANES)

func to_world_x(local_x: float) -> float:
	return C.wrap_x(local_x - x_shift)
```

### Что переводить

**С сервера на клиент** (в снимках состояния / событиях):

| Данные | Перевод |
|---|---|
| Дорожка серфера | `to_local_lane` |
| X акул, большой акулы, торнадо, ракет, цели бомб и молний, сундуков, меток гибели | `to_local_x` |
| Y всего | без изменений |
| Направление движения (`dir` акул, торнадо, ракет) | без изменений |

**С клиента на сервер** (ввод):

| Ввод | Что отправлять |
|---|---|
| Держит / отпустил палец, держит пляж | как есть, без координат |
| Рывок вверх / вниз | как есть (`dir = ±1` по Y) |
| Ракета влево / вправо | как есть (`dir = ±1` по X) — направление не переводится |
| Бросок бомбы | цель: `Vector2(to_world_x(local.x), local.y)` |
| Тап по сундуку / кубку | лучше отправлять **id предмета**, а не координаты |

### Что ещё учесть на клиенте

- **Отрисовка у края экрана.** Объекты рисуются через `ring_copies` по своему X. После перевода
  в локальные X это продолжает работать: швом для клиента становятся края его экрана.
- **Ник, цвет и лежак серфера** определяются мировой дорожкой (`SURFER_COLORS[lane]`, `BOT_NAMES[lane]`).
  В онлайне цвет и ник нужно брать от игрока, а не от видимой дорожки, иначе у каждого клиента
  цвета будут свои. Позиция лежака — по локальной дорожке.
- **Подсветка «своя дорожка»** — всегда `PLAYER_LANE` (локально это и есть свой игрок).
- **`PLAYER_LANE` в одиночной игре** продолжает означать «дорожка живого игрока»; в онлайне
  это «куда клиент ставит себя после перевода».

### Альтернатива (не рекомендую для первого шага)

Хранить на клиенте мировые координаты, а сдвигать только при отрисовке
(`visual_x = wrap_x(world_x + x_shift)` в каждом `_draw` и в `position` узлов).
Это требует разделить «модельную» и «видимую» позицию у каждого объекта и пересчитать
`ring_copies` по видимому X — заметно больше правок по всему коду.

## 5. Что пока не готово для сети (общее, не только про кольцо)

- **Случайность.** Используется глобальный `randf()` / `randi()`. Для серверной симуляции
  достаточно, чтобы случайность была только на сервере. Если понадобится, чтобы клиент сам
  предсказывал события (или для ежедневного забега с одинаковым раундом), нужен
  `RandomNumberGenerator` с сидом, общий для всех.
- **Логика в одном файле.** `scripts/main.gd` (~1400 строк) держит и симуляцию, и отрисовку,
  и ввод. Для авторитарного сервера симуляцию стоит вынести отдельно от отрисовки.
- **Ввод и бот — в одном классе.** `surfer.gd` содержит и движение, и мозг бота (`_bot_think`).
  Для онлайна стоит отделить «управление» (живой игрок / сетевой игрок / бот) от «серфера».
- **Боты** нужны и в онлайне: добирают матч, если живых меньше пяти. Их решения должны
  приниматься на сервере.
